# Правила разработки и работы с репозиторием «Забота на дому»

## 1. Соглашение по именованию веток
Основная ветка проекта — `main` (содержит только стабильный, проверенный код). Прямые коммиты в `main` запрещены.

Формат рабочих веток: `<тип>/<модуль>-<краткое-описание>` (на английском языке в нижнем регистре через дефис):
- `feature/...` — разработка нового функционала (пример: `feature/backend-sos-endpoint`, `feature/web-visits-table`)
- `bugfix/...` — исправление ошибок (пример: `bugfix/mobile-checklist-status`)
- `docs/...` — обновление документации и тест-кейсов (пример: `docs/qa-test-cases`)
- `refactor/...` — оптимизация кода без изменения логики

## 2. Правила оформления коммитов (Conventional Commits)
Формат сообщений: `<тип>: <краткое описание>`
- `feat:` — добавление новой функции
- `fix:` — исправление бага
- `docs:` — изменения в документации
- `style:` — форматирование кода
- `refactor:` — рефакторинг кода
- `test:` — добавление или исправление тестов

## 3. Стандарты написания и комментирования кода
- **Backend (Python / FastAPI):** стандарт **PEP 8**. Переменные и функции — в `snake_case`, классы — в `PascalCase`. Обязательны аннотации типов (Type Hints) и Docstrings.
- **Web & Mobile (React.js / TypeScript / Dart):** стандарт **Airbnb Style Guide** / **Effective Dart**. Переменные и функции — в `camelCase`, компоненты и классы — в `PascalCase`. Соблюдение стандартов доступности (контрастность, масштабируемость шрифтов).
- **Комментирование:** комментарии пишутся на русском языке для пояснения сложной бизнес-логики. Очевидный код не комментируется.

## 4. Процедура Code Review и Pull Request (PR)
1. После завершения задачи разработчик отправляет ветку в GitHub и открывает **Pull Request** в ветку `main`.
2. В описании PR указывается перечень изменений и ссылка на задачу в таск-трекере.
3. **Распределение проверки:**
   - Код Frontend/Mobile (Дзагоев Т.) проверяет тимлид Бадов В.
   - Код Backend (Бадов В.) проверяет Дзагоев Т.
   - Функциональное тестирование по чек-листам проводит Жамурзаев М.
4. Слияние (Merge) в `main` выполняется только после получения минимум одного подтверждения (**Approve**) и отсутствия конфликтов. После слияния рабочая ветка удаляется.
